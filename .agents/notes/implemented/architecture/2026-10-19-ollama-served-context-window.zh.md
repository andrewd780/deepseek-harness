# Agent Note：pi-ai 获取 Ollama 端点实际提供的上下文窗口

Status: implemented

[English](2026-10-19-ollama-served-context-window.md) | 中文

## 问题

在 Models 页面添加、Context window 留空的自定义端点会解析为 pi-ai 的 262,144-token 默认值。Ollama 实际提供的窗口小得多：它在加载模型时确定窗口——来自 Modelfile 的 `num_ctx`、`OLLAMA_CONTEXT_LENGTH`，或按显存分档的 4,096、32,768 或 262,144 tokens 默认值，加载失败后还可能降低——其 OpenAI 兼容聊天处理器会在请求放不下时丢弃最早的非系统消息，且不报错。因此 harness 从未在 Ollama 截断之前压缩，长时间的 `/goal` 对话可能在没有任何信号的情况下丢失最早的消息（包括目标本身），而报告的那一轮以错误结束。仅仅声明真实窗口还不够：同一模型可能按服务端环境以 32,768 或 8,192 tokens 提供，而且在模型加载之前，没有任何 Ollama API 报告这个窗口。

## 决策

`dsh-llm-pi-ai` 在声明路由（已安装目录未提供的路由）上探测 Ollama 的进程列表 `GET {root}/api/ps`，前提是路由带 `baseURL` 且使用 OpenAI 或 Anthropic 协议，并且没有设置 `servedContextProbe: off`。每次 `resolveModel()` 都会探测；同一路由的并发探测共用一次请求，时限为 `servedContextProbeTimeoutMs`（默认 5,000 ms）。列表中某模型的 `context_length` 按路由与规范化的 Ollama 模型名学得并保存在内存中，因此已卸载的模型保留最近一次观察到的窗口。适配器从 `resolveModel()` 与预备调用报告 `min(配置窗口, 学到的窗口)`，并把带这个窗口的模型描述交给 pi-ai，使其输出上限钳制和基于用量的溢出检测都使用它；若请求的 pi-ai 估算值超过学到的窗口，适配器会在网络 I/O 之前以 `CONTEXT_WINDOW_EXCEEDED` 拒绝请求，把历史交给压缩的溢出恢复处理。不是进程列表的响应会把该路由标记为不探测，直到其配置变化；暂时性失败会在下一次查询时重试。运行规则以[包 README](../../../../packages/llm/llm-pi-ai/README.zh.md) 为准。

## 考虑过的替代方案

**只在模型发现时读取窗口。** 未采用：发现结果一经采纳就成为存储的配置，因此服务端以 32k 运行时得到的值，在服务端改为 8k 后会成为过时的上限；而且发现无法看到未加载的模型。

**使用 `/api/show`。** 未采用：其 `model_info` 中的上下文长度是训练长度，`parameters` 只在 Modelfile 设置时才包含 `num_ctx`；两者都不报告服务端实际采用的环境变量或显存默认值。

**在探测前加载未加载的模型。** 推迟：它能消除重启后第一个请求的缺口，但列出模型目录时也会查询模型信息，在那里加载每个列出的模型是不可接受的副作用；在发送路径上加载需要自己的生命周期。

**根据报告的提示 token 数检测截断。** 未采用：差额含义不明确，因为曾观察到 Ollama 报告的提示 token 数不包括复用的缓存前缀（未在 Ollama 源码中核实），所以它无法证明发生了截断。

**只在用户选择启用时探测。** 不作为默认：报告问题的部署把所有容量字段都留空，需要用户自己发现的开关无法修复它；`off` 仍可使用，而非 Ollama 路由只会以一次 404 应答，此后不再被探测。

## 影响

在 Ollama 路由上，一旦某次查询看到模型已加载，压缩就按实际提供的窗口定价，因此留空的 Context window 会在推导出的默认余量下主动压缩（32,768-token 窗口在 26,214 tokens 时压缩），而仍会被截断的请求会以已分类的溢出失败，由压缩恢复。每个带端点的声明路由在每次配置变化时多一次 GET，Ollama 路由在每次查询模型信息时多一次 GET。在本进程的任何查询看到模型已加载之前发出的请求——例如 Host 重启后、Ollama 已卸载模型时的第一个请求——仍使用配置窗口。发送前检查与 pi-ai 共用每 token 四个字符的估算，对分词较密的文字会少计。只有 Ollama 会被探测；LM Studio、llama.cpp 与 vLLM 在其他位置报告其窗口。

## 测试

`served-context.spec.ts` 覆盖按路由类型与设置解析探测、规范化模型名、列表校验、每种探测结果（列表、非列表应答、暂时性状态、不可达与停滞的端点、凭据失败）、共用探测、按调用方取消、释放，以及发送的请求头；通过适配器，它固定了报告的窗口、只警告一次、pi-ai 按实际窗口钳制输出、更小的配置窗口、`off` 设置，以及请求到达端点之前的发送前拒绝。`loader-composition.spec.ts` 通过 Loader 启动插件，使用没有容量字段的声明路由，断言学到的 32,768-token 窗口与钳制；`egress.spec.ts` 让探测经过配置的代理。若 tracker 未接入、pi-ai 收到配置的描述，或移除发送前检查，插件级测试都会失败。
