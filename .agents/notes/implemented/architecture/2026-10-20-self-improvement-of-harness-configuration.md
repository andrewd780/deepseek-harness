# Agent Note: Self-improvement evolves harness configuration measured in fresh runtimes

Status: implemented

English | [中文](2026-10-20-self-improvement-of-harness-configuration.zh.md)

## Problem

Regularized recursive self-improvement (RRSI, arXiv 2609.24972) improves an agent harness by search: a model proposes edits, and edits that measurably raise the score on a task suite are kept. Its [reference implementation](https://github.com/google-research/rrsi) evolves a Python agent scaffold kept in its own repository, measures it on Terminal-Bench through containers, and calls its search roles through one cloud provider. None of that runs in a dsh composition, and an accepted change to dsh would still need porting by hand into packages that carry full coverage, snapshot, and documentation obligations. The search also measures on the same tasks it optimizes, so without the reference's regularizers a run accepts noise, edits that fit the suite, and machinery that never pays for its tokens.

## Decision

`@deepseek-ai/dsh-experimental-self-improve` reimplements the reference loop in TypeScript, following the paper's text where the two differ, and evolves a directory of dsh configuration: a profile overlay, user-global `AGENTS.md`, and skills, tracked in the operator's repository. Each candidate is a branch with its own git checkout; accepted candidates fast-forward an evolve branch and never change the operator's working tree. A trial runs one task in a fresh `dsh` runtime started through the SDK client, with the candidate's overlay applied before frozen policy patches and a fresh workspace, Harness home, and agents home outside any repository; the task's checks score it, and its cost is the exact turn usage of every Session in the runtime. Every trial loads the overlay as configuration that could load plugins, start processes, or loosen the sandbox, so a candidate's overlay may only set a fixed list of tuning settings and turn tools off; the plugin checks it before review, and a trial loads a JSON copy of the checked entries. The analyst, proposer, and critic call `ctx.llm` outside any Session, and the run directory keeps every draft's model interaction and every verdict. Runs start from the `/self-improve` command, or from a daily schedule the command or the plugin settings turn on, as background jobs owned by a session.

Without arguments, `/self-improve` runs an automatic mode: it creates a starter run from a template bundled in the package, runs the baseline, calibration, every round, held-out measurement, the apply, and a summary as one job that resumes from the run's stored state, and follows a finished run with a generation that starts from its result. The apply writes an accepted result where dsh reads configuration: the overlay's entries, checked against the overlay rules again, into a managed section of the Harness home's patch layer, which every profile applies last and dsh's own editors never write; `AGENTS.md` into a managed section of the user-global instructions; and skills into the user skills. It backs up every path it changes with a manifest first, refuses to replace content an apply did not write, and undo reverses the newest apply section by section; an undone result is never applied again. The [package README](../../../../packages/experimental/self-improve/README.md) owns the operational rules.

## Alternatives considered

**Run the reference implementation with a dsh adapter.** Rejected as the implementation: it keeps the single-provider search roles, the benchmark containers, and an evolved copy outside this repository, and its accepted diffs still need porting. An adapter remains the route for reproducing the paper's Terminal-Bench measurements.

**Follow the reference implementation where the paper's text differs.** Rejected: the paper specifies the method and the reference is one realization of it. The reference shows the proposer no source diffs although the paper's proposer conditions on them, ends the edit budget above the paper's final-round budget, and rejects grounds the paper's critic does not name; the [package README](../../../../packages/experimental/self-improve/README.md#dev-note) lists each difference.

**Evolve TypeScript sources.** Rejected for now: every candidate would need a build and the full gates before measurement, estimated at 15 to 40 minutes each, and an accepted change still carries every package obligation. Configuration changes ship as an overlay the operator applies.

**Measure candidates as in-process subagents.** Rejected: in-process children share the host process, its services, and the parent's preset, so a candidate's overlay cannot apply, and their results carry no token usage.

**Run the proposer and analyst as spawned subagents.** Deferred: subagents record their requests in Session logs and bring the harness's file tools, but a run would need a live parent agent for hours and an activation lifecycle for structured output. The JSON action protocol keeps the proposer inside the candidate's evolved directory with a bounded number of requests.

**Expose a model tool.** Rejected: a tool would let a model start runs costing thousands of trials and add schema tokens to every request; the command, and the schedule only an operator turns on, keep starting a run an operator decision.

**Leave every apply to the operator.** Rejected for the automatic mode: an unattended daily run helps only when its result reaches the operator's Sessions, so the apply is automatic and made reversible by backups, refusals, and undo instead. Explicit runs still apply only on `/self-improve apply`.

**Write the overlay into the profile's own patch.** Rejected: dsh's plugin manager and settings pages write that file and add rows at its end, which would land them inside a managed section that the next apply replaces. The home patch layer has no such writer and applies after the profile's patch, as a trial's overlay applies after the trial profile.

**Apply only a gain above the noise band that the held-out tasks confirm.** Not adopted: the apply follows the run's own acceptance rule, which admits a candidate within the band for a token saving or a new structural component, and the summary reports the held-out scores beside it.

## Consequences

A run can tune dsh for the operator's own task suite, model route, and context window, including a small local window, because the spec supplies the trial route and patches. Improvements are limited to what configuration expresses. Every candidate costs a full measurement of the evolve tasks: at the reference constants, about 82 trials per task over a run. The search roles' requests are kept in the run directory, not a Session log, because they run outside any Session. Whether dsh reaches gains like the reference's is unmeasured: the reference reported them for other policies and harnesses. The automatic mode changes the operator's live configuration without a person present; backups, refusals, and undo bound that change, and an applied overlay was measured on the trial profile, so in another composition an entry can change nothing or replace configuration that profile's bundles set.

## Testing

Unit specs cover the selection arithmetic, edit budget, history summaries, calibration, critic, the overlay rules with each rejected form and their enforcement before review and before any trial, the proposer's action protocol and its path checks, suite validation and checks, the git store against real repositories, run-directory validation, and the loop's gates and resume; trials run against the SDK client's scripted runtime. Automatic-mode specs check every starter task against a reference solution and its starting files, the run's creation, the pipeline's resume and generations, apply and undo with their backups and each refusal, and the schedule's checks with a scripted `vm_stat`; `loader-composition.spec.ts` also runs `/self-improve` alone on the starter run through the Loader. `loader-composition.spec.ts` boots the plugin through the Loader with commands, background jobs, a real subprocess provider, and a scripted model, measures a baseline, accepts a new skill in a round, and asserts the evolve branch, the history, the held-out score, and that disposing the plugin removes the command. `real-runtime.e2e.ts` runs a baseline, a round, and a held-out pass with every trial in a fresh `dsh` runtime started through the SDK client; the runtime's policy route reaches a local OpenAI-compatible stand-in that formats its answers only when a request carries the output contract, so the round accepts the instruction edit only when the evolved `AGENTS.md` reaches the runtime's model requests.
